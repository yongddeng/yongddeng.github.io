Deployment · Concurrency vs Parallelism

FastAPI agent server on a 4-core instance

A mixed workload: most requests are I/O-bound (LLM API calls) and belong on the event loop; a request that spawns a Python executor is CPU-bound and belongs in a separate process. Serve both by splitting the box asymmetrically.

I/O path — stays on the event loop CPU path — offloaded to a separate process
  • 1The loop is never the CPU-bound part. Even on a compute request it only awaits the result — the work runs in a distinct process the OS schedules on any free core, so don't pin cores to "loop vs compute".
  • 2Not four Uvicorn workers. Four event loops is overkill for I/O, and a compute burst then has no dedicated processes — it stalls a loop inline or oversubscribes the cores.
  • 3Asymmetric split. A few event-loop workers + an executor pool, total processes ≈ cores. Because the server leg is nearly pure I/O, spend most of the box on the executor.
  • 4Concrete. gunicorn -k uvicorn.workers.UvicornWorker --workers 2 + ProcessPoolExecutor(max_workers=2), with a queue and per-task timeout. Arbitrary code → prefer a killable subprocess per run.

Optional: an Nginx reverse proxy in front terminates TLS and buffers slow clients. Containerised, drop Gunicorn and let Kubernetes replicate one-worker pods.
